技术架构文档 · 2026-08

onto-studio：全生命周期可视化本体建模工具

将客户专家知识和业务体系、客户系统与流程萃取为可计算的本体模型与知识图谱—— Tauri 2 单二进制承载「Agent 对话 + 多模态文件摄取 + 跨源联邦查询 + Skill 扩展」四件事， 以五条原则和 20 条 ADR 把"零安装"与"能力完整"这对矛盾逐个化解——PDFium 破例、agentic search 砍 RAG、 rig 原生 CompactingMemory、DataFusion 单进程联邦。

📦 Tauri 2.11 + Rust 1.97 🗄️ 单文件 SQLite（bundled + FTS5） 🤖 Rig 0.41 + rmcp 1.x 📄 13 种文档格式 ⚡ 13 个 LLM provider

0用户视角：onto-studio 能做什么

onto-studio是一款全生命周期可视化本体建模工具——将客户专家知识与业务体系、 客户系统与流程萃取为可计算的本体模型与知识图谱，支撑从需求分析、本体设计、数据源接入到 联邦查询的全链路。底层是一个能读所有文件的可对话 AI、一个可扩展的工具台、一个随装随用的本地应用。

下文将系统架构映射为用户可感知的五项系统能力。每项能力回答三个问题：用户能做什么、 怎么触发、能力边界在哪。这不替代后续的技术章节——技术章节解释这些能力为什么这样设计、 权衡是什么——而是先给读者建立"这个工具对我的本体建模工作能帮什么忙"的全局认知。

能力一 · 通用 AI 对话（13 个模型，任意切换）

onto-studio 首先是一个 AI 对话客户端。与 ChatGPT 网页版的不同在于：本地运行、 数据不离机、模型随意换。支持 13 种 LLM provider（DeepSeek / OpenAI / Gemini / Anthropic / Groq / OpenRouter / Ollama / Moonshot / Mistral / Cohere / Perplexity / xAI / 兼容端点），以及支持图片输入的 VLM 模型（Gemini / GPT-4V / Claude）。

对话支持流式渲染、推理过程展开（DeepSeek-R1 思维链）、工具调用可视化 （模型调了哪些工具、每个工具返回了什么，以卡片形式展示在对话流中）。 会话自动持久化到本地 SQLite，关闭再打开对话历史不丢。 长对话自动压缩——当 token 预算触及上限时， 系统用当前运行的模型生成滚动摘要，裁剪旧消息保持上下文在预算内，用户无感。

典型场景：本体萃取
「客户给了一份 200 页的产品需求 PDF 和一套数据库 schema，帮我从中提取业务对象和关系， 构建一个初步的本体模型」→ 拖入 PDF + 注册数据源 → AI 自主检索文档和 schema → 按 ObjectType / LinkType / ActionType 框架输出本体清单，引用原文。 全程数据在本地，对话记录和文件都不上传到模型厂商服务器（除非模型 API 本身需要上传， 用户可以选本地的 Ollama 完全离线）。

能力二 · 文档摄取与全文检索（13 种格式，一个入口）

onto-studio 能读的文件类型覆盖了知识工作者日常接触的绝大部分：

类别 格式 能力说明
文本 .txt · .md · .json · .csv 直接读，自动检测编码
PDF .pdf 中文完美（Chrome 内核渲染，无乱码）
Office .docx · .pptx · .doc · .xls · .ppt 含老格式 DOC/XLS/PPT，保留标题/段落/表格结构
Excel .xlsx（读）+ .xlsx（写） 保留类型和公式，精细读；可程序化写出
电子书 .epub 按章节读，保留 spine+manifest 结构
图片 PNG / JPEG / GIF / WebP / BMP 直接传给 VLM 模型做视觉理解（OCR / 图表 / 照片分析）
压缩包 .zip · .tar · .tar.gz 递归解压内部文件，防炸弹（200MB 文件 / 500MB 总量 / 5 层深度）

所有文件拖入后自动建全文索引（中文分词 + BM25 排序），AI 对话中能按需检索文件内容—— 不需要用户手动告诉 AI "去查哪个文件"，AI 根据自己的判断自主决定是否调搜索工具。

能力三 · 可扩展工具台（MCP + Skill）

除了内置的文件检索工具，onto-studio 支持两种扩展方式让 AI 获得更多能力：

扩展方式 用户做什么 AI 能多干什么 适合谁
MCP Server 在设置页填 MCP server 命令（如 npx @anthropic/mcp-server-filesystem）或 HTTP URL 读写本地文件系统、查数据库、调 API、搜网页——任何有 MCP server 封装的能力 开发者 / 有 MCP 生态认知的用户
Skill 导入一个 SKILL.md 文件（YAML frontmatter + Markdown 正文），或从社区下载 获得领域专用的提示词模板和行为约束（如"用公司财报分析框架回答问题"），但不执行代码 所有用户 / 社区贡献者

MCP 和 Skill 的互补关系： Skill 是「教 AI 怎么想」——注入领域知识和行为框架，纯文本，零安全风险。 MCP 是「给 AI 一双手」——让 AI 做实际操作（读写文件、查数据库、调 API）， 需执行能力的 Skill 走 MCP server 封装。两者统一注入 Agent 的工具系统， AI 在对话中按需选择用哪个。

用户控制粒度
Skill 有三级开关：① 单个 Skill 的 SKILL.md frontmatter 声明关闭 → ② 全局禁用列表（disabled_skills 表）→ ③ 会话级激活列表（conversation_skills 表）。 用户可以全局关闭某个 Skill，但某个会话里临时打开它——精确控制哪些 Skill 在哪些场景下生效。

内置 3 个开箱即用的 Skill: pdf-reading（PDF 文档阅读与信息提取框架）、 spreadsheet-analysis（电子表格分析框架）、 mcp-user-feedback（用户反馈收集与 MCP 工具迭代）。

能力四 · 跨数据源联邦查询与模型验证（三期）

本体建模的最终验证是"这个模型能正确回答业务问题吗"。onto-studio 直接连接客户结构化数据源 （MySQL / PostgreSQL / CSV / Excel），注册后用自然语言发起跨源查询来验证本体模型是否正确覆盖了 客户系统的真实数据关系。

典型场景：模型验证
客户有一个 MySQL 用户库和一个 PostgreSQL 订单库。本体模型定义了 User 对象、Order 对象、 User-[places]-Order 链接。验证时的自然语言查询：「上个月下单超过 3 次的用户里， 哪些最近 7 天没登录？列出邮箱。」→ AI 理解本体语义 → 规划跨源 SQL → DataFusion 联邦执行 → 结果确认本体关系的基数/方向是否正确。用户不需要手写 JOIN——AI 先 browse_schema 理解表结构再生成查询。

安全护栏：所有联邦查询只读（自动拒绝 DDL/DML），自动 LIMIT 注入（默认 200 行， 最大 1000），30 秒超时。数据源凭证加密存储在本地 SQLite，不出设备。

能力五 · 零安装本地运行

以上所有能力在一个二进制文件里。安装体验：下载 → 双击运行 → 配置模型 API key → 开始对话。 不需要装 Python / Node / Docker / LibreOffice / PostgreSQL / 任何运行时或系统库。 数据全部存在本地 ~/.onto-studio/onto-studio.db 一个文件里，便携备份。

桌面端（Win / Mac / Linux）完整功能，移动端（已落地）单套代码 + 自适应布局—— 对话和文件浏览在手机上可用，复杂配置建议桌面操作。

1系统总览

onto-studio 是一款全生命周期可视化本体建模工具—— 将客户专家知识与业务体系、客户系统与流程萃取为 ObjectType / LinkType / ActionType 本体模型， 支撑从需求分析、本体设计、数据源接入到联邦查询的全链路。底层是对话 LLM、文档摄取、 跨数据源查询、Skill 扩展统一在一个零安装的桌面二进制里，业务核心全 Rust、平台层只做 Tauri IPC 薄壳。

这个项目要回答的核心问题是：能不能用纯 Rust 单二进制做到零安装，同时不牺牲中文 PDF 解析、 Agent 工具编排、跨源联邦查询？ 现有方案要么是 Electron 重壳加多运行时（Python/Node/Java 子进程）， 要么依赖 LibreOffice / Tesseract / PostgreSQL 等用户需自行安装的系统组件，要么 RAG 路径撑爆 context。 onto-studio 的答案是原则驱动的约束——先用五条不可动摇的原则画死边界，再用 20 条 ADR 在边界内逐个化解矛盾。

五条原则（贯穿所有决策，优先级最高）

原则 1
Rust 纯栈，运行时零额外原生依赖
用户拿到二进制即可运行，无需装任何系统库/运行时/办公软件。SQLite 随源码静态编译，PDFium 预编译库随安装包分发。绝对否决 LibreOffice / FFmpeg / Tesseract / Poppler / OpenSSL / 独立向量库。
原则 2
轻量化
不内嵌本地模型权重（OCR / Whisper / VLM 一律不走本地重型模型）。重型能力走 API，本地推理由用户自配 Ollama 接入。
原则 3
许可证友好
全部 MIT / Apache-2.0 / BSD-3，排除 GPL。引入新 crate 前先核实许可证（如 eBook 否决 GPL 的 epub crate，改用 Apache 的 rbook）。
原则 4
业务核心与平台解耦
业务逻辑全在 crates/（平台无关，可独立 cargo test），Tauri 只做 IPC 薄层 + 平台能力，DocumentParser trait 抽象底层库可平滑替换。
原则 5
外部服务最小化且显式
仅两类外部依赖：模型 API（云端 LLM/VLM 或用户自配 Ollama）、MCP server（用户按需接入的工具服务）。两者都显式可知，无隐式后台调用。
唯一破例 · 决策 5
纯 Rust（lopdf / pdfsink-rs）对中文 CID CMap 解码失败，仅 PDF 解析破例引入 pdfium-render + 预编译 PDFium 动态库（BSD-3-Clause，随安装包分发，用户零安装）。这是纯 Rust 文本提取能力不足的工程妥协，不开放其他否决项。

五条原则不是口号，是选型否决的硬边界。下文每个 ADR 都会回到这些原则解释为什么选 A 不选 B—— 比如联邦查询否决 Trino（JVM 独立进程，违反原则 1）、TextQL 否决 Python sqlglot（需 Python 运行时）、 数据源连接否决 SQLAlchemy、Office 否决依赖 LibreOffice 的 LiteParse。这些否决不是事后找补，而是设计之初就画死的红线。

2四层架构：业务核心与平台解耦

自上而下四层单向依赖——表现层（WebView）→ IPC 薄层（Tauri）→ 业务核心（crates/）→ 平台插件。 业务逻辑全部在 crates/，平台无关可独立测试；Tauri 只做 #[tauri::command] 薄封装。

这个分层不是装饰——它是可测试性的硬保证。根 Cargo.toml 明确 exclude = ["src-tauri"]，cargo check --workspace 只验证 crates/*， src-tauri 有独立 target 目录与构建流程（避免 Tauri 的 wasm/mobile target 与业务 crate 的 feature unification 冲突）。 这意味着crates/可以在无 Tauri 环境的 CI 里跑全部单元测试，业务逻辑的回归不依赖 GUI。

工程结构硬约束

  • 业务逻辑禁止放进 src-tauri/——src-tauri/src/commands/ 下每个文件只是 #[tauri::command] 薄封装，调 crates/ 的 service
  • crates/ 之间可互相依赖，但不得反向依赖 src-tauri/ 或 src/——依赖方向永远向下
  • 前端四层单向依赖：UI → State → IPC → Domain，用 ESLint no-restricted-imports 在 CI 强制（components/ 不得直接 invoke，stores/ 不得 import 组件）
  • IPC 类型安全：tauri-specta 从 Rust #[tauri::command] 自动生成 TS 绑定，禁止手写 TS 类型

2.1多模态摄取管道

DocumentParser trait 统一 13 种格式，dispatcher 按扩展名 + magic bytes 路由， PDF 走 PDFium 进程级锁串行化，Office 走 office_oxide 统一 IR，全程流式解析防 OOM，zip 炸弹有预算守卫。

PDFium 破例的工程细节

这是整个项目唯一破例引入非 Rust 原生依赖的地方，也是最容易翻车的工程点。三个关键约束决定了它必须这样实现：

  • 为什么不纯 Rust：实测《曾国藩合集》1371 页（Type0 + CIDFontType2 + SimSun 子集 + ToUnicode CMap），lopdf 输出纯乱码（第 2 页仅 42 字符拉丁符号），pdfsink-rs 输出空。pdfium 是 Chrome 内核，渲染级文本提取，1371 页全量 4.15s，中文完美。
  • 为什么用预编译库而非编译 C++：全程使用 bblanchon/pdfium-binaries 社区预编译二进制（BSD-3-Clause），pdfium-render 仅做 FFI 绑定，cargo build 只编译 Rust 代码，无 GN/Ninja/Chromium 编译链。库随 Tauri bundle.resources 打包进安装包，用户零安装。
  • 为什么必须进程级 Mutex 串行化：pdfium-render 0.9.3 的 thread_safe feature 仅 impl Send+Sync，不串行化 FFI 调用——native 路径每个 FPDF 函数直接调函数指针无锁。而 PDFium C 库本身非线程安全（fpdfview.h 明确要求调用方加锁）。多文件 batch 并发解析会导致内存损坏（STATUS_STACK_BUFFER_OVERRUN）。故 crates/ingest/src/pdfium.rs 用进程级 Mutex<()> 令牌锁 with_pdfium() 串行化所有 PDFium 操作。
代价与权衡
多文件 batch 实际串行执行 PDF（非 PDF 文件不受锁影响仍并行），性能依赖单文件速度（实测 1711 页 4.5s，可接受）。库版本 pdfium_7881 feature 必须与下载的 PDFium 版本严格一致，否则 bind() 崩溃。

Office：统一 IR 与独家能力

office_oxide 0.1.8（2026 年 4 月新库）统一处理 DOCX 读/写、PPTX、老格式 DOC/XLS/PPT，产出结构化 IR（标题/段落/列表/表格/页眉页脚/图片，保留交错顺序），对 agent/RAG 场景比扁平 MD 更顺手。老格式 DOC/XLS/PPT 是纯 Rust 生态的独家能力。XLSX 读单独保留 calamine——office_oxide 的 IR 把单元格扁平为 string 丢失类型/公式，精细读 Excel 是损失。

选型时决定性否决了 LiteParse v2：它依赖 LibreOffice 系统安装，无法对用户隐藏，违背原则 1，且 Office 转 PDF 再解析丢失原生结构。DocumentParser trait 隔离使 office_oxide 这种极新库（0.1.x）可平滑回退——落地需做兼容性自测（放 crates/ingest/tests/）。

安全防护：防 zip 炸弹与 OOM

crates/ingest/src/security.rs 的 ArchiveBudget 守卫：文件大小上限 200MB，解压总量 500MB，条目数 10K，递归深度 5 层。压缩包走流式解析，不在内存持有全部内容。这是对抗恶意输入的硬约束。

2.2Agent 内核：Rig + MCP + Skill

Rig 0.41 驱动 agent loop，ProviderRuntime trait 擦除泛型统一 13 个 provider， rmcp 1.x 自实现 DynamicTool 桥接 MCP 工具，agent-skills 0.2 实现 agentskills.io 规范的 Skill 渐进式披露。

ProviderRuntime：擦除泛型消除 match 分支

Rig 的 Agent<M> / Client<Ext,H> 是高阶泛型，不同 provider 具体类型不同，无法直接 trait-object 化。决策 7.5 引入 ProviderRuntime trait——把"构造 agent + 设采样参数 + 流式/prompt"封装为返回已擦除类型（StreamChunk 流 / String）的 method。每个 provider kind 在 with_tools 时构造具体 client 并立即包成 Box<dyn ProviderRuntime>，ChatService 持 trait object，所有调用点零 match 分支。新增 provider 只需两步：① build_runtime 加构造分支 ② 宏 impl_provider_runtime! 生成 trait impl。

P0 正确性修复
早期方案把 DeepSeek 塞进通用 openai::Client.completions_api()，丢失 rig 的 OpenAICompatibleProvider capability 声明（DeepSeek 的 EMITS_COMPLETE_SINGLE_CHUNK_TOOL_CALLS=true、SUPPORTS_RESPONSE_FORMAT=false）——可能导致流式 tool call 渲染异常、response_format 被错误发送触发 400。按 kind 路由后各 provider 的 capability 由 rig 正确声明。

MCP：版本锁定的工程理由

锁定 rmcp ^1.8 而非 3.0-beta，是编译可行性的硬约束：rig 0.41 依赖 rmcp 1.x，若直接用 3.0-beta 会与 rig 拉的 1.x 共存，且 rmcp 3.x 的 macros feature 依赖 pastey/darling，在当前 toolchain 触发 cargo resolver panic。不启用 rig 的 tool::rmcp feature（它针对 3.0-beta API），自实现 DynamicTool 桥接只需 rmcp client + 两个 transport feature，无 macros。

stdio transport 自实现而非用 rmcp 的 transport-child-process——后者依赖 process-wrap 拉入 windows crate 重型包，当前 toolchain 编译失败。改用 tokio::process::Command spawn + rmcp 的 (AsyncRead, AsyncWrite) transport，零额外原生依赖（符合原则 1），Windows 下设 CREATE_NO_WINDOW 避免弹控制台。

Skill 系统：文本扩展而非可执行插件

决策 20 基于 agentskills.io 开放规范。Skill = SKILL.md（YAML frontmatter + Markdown 正文），不是可执行插件——需执行能力的 skill 走 MCP server。渐进式披露分两层：Tier 1 是 name + description 常驻 preamble（几十 token），Tier 2 是完整正文按需由模型调 read_document 读取（skill body 入库 documents 表走 skill://<name> doc path，与 @ 挂载统一路径）。

三层 disable：frontmatter disable-model-invocation（层次 1，Govcraft 不解析业务层补）→ 全局禁用 disabled_skills 表（层次 2）→ 会话级激活 conversation_skills 表（层次 3）。四类来源：Builtin（随应用分发，只读）/ Imported（用户导入，可写）/ ExternalReadOnly（跨客户端 ~/.claude/skills 等扫描）/ Project。preamble 段拼在系统人设之后保 prefix cache，<available_skills> XML 手写极简转义零依赖，空列表返回空串不破 prefix cache。

2.3上下文架构：agentic search 砍 RAG

砍掉向量 RAG，改用「文件工具 + FTS5 全文搜索」的 agentic search 模式——模型按需调 search_documents/read_document 检索，而非自动注入切片。@ 挂载只保留位置语义 token + user message 尾部注脚，不注入全文，prefix cache 友好。

为什么砍 RAG：业界共识 + 三原则协同

  • 业界共识（2026）：小语料文件工具优于 RAG（Anthropic 在 Claude Code 用 agentic search 替换 RAG，+2.7% 准确率）。onto-studio 是本体建模工具（几十到几百文档），适合文件工具模式。
  • FTS5 是白送的能力：bundled SQLite 默认编译 -DSQLITE_ENABLE_FTS5，支持 BM25 排序、snippet 高亮、external content table（全文只存一份），无需加任何依赖。
  • 口语化 query 问题在工具路径下不存在：用户口语化长 query 直接做 FTS5 MATCH 会翻车，但走文件工具路径，query 来自模型的 search_documents 调用——模型天然会把口语化意图转成搜索关键词。
  • 三原则协同：无需 embed API（原则 5 外部服务最小化）、无本地 embedding 模型（原则 2 轻量化）、无 sqlite-vec（少一个原生扩展，原则 1）。
jieba 分句版 tokenizer · 200 倍提速
替代 sqlite-jieba-tokenizer 0.6——该 crate 的 tokenize 直接对整段文本 JIEBA.cut(text, true)，jieba DAG 对超长连续文本 O(n²) 退化（1.4M 字符 PDF 需 600s+）。自实现分句版先按标点/换行分句再逐句 cut，offset 按 byte 精确累加，实测 600s → 2.91s（提升 200 倍）。stopword/stemmer/小写归一化逻辑与原版一致，索引兼容。

`@` 挂载：位置语义 + prompt cache 友好

决策 17 推翻了早期"全文注入"设计。核心是 prompt cache 友好的上下文架构——prompt caching 是 prefix match，前缀任意一字节变化后面全失效。因此：

  1. 静态前缀冻结：tools 定义、system prompt 在会话期间永不变化，动态状态绝不进 system prompt。
  2. 挂载信息进 user message：用户 @ 的文档清单作为 <mounted-documents> 注脚追加到本轮 user message 尾部，每轮变化但不影响已缓存 prefix。
  3. 不给摘要：注脚只给 id + name，避免 batch 上传多文档时生成摘要的延迟，文件名已足够模型决策。
  4. 不注入全文：模型按需调 read_document(id) 工具分页读取，与未挂载文档走同一套路径完全统一。
prefix cache 经济性
18k tokens 静态前缀，50 轮会话：无缓存 $13.50 vs 有缓存 $1.35（差 10 倍，仅前缀成本）。system prompt 塞文件清单会每轮失效，成本飙升。Anthropic static-first 架构（Claude Code 实现）达成 90-96% cache hit rate。

CompactingMemory：复用 rig 原生，不手写 trim

决策 16 直接复用 rig 0.41 + rig-memory 0.41 的上下文管理基础设施。crates/agent-core/memory_bridge.rs 把项目 Memory（SQLite）适配为 rig ConversationMemory（newtype SqliteMemory 绕过孤儿规则），再挂 CompactingMemory 组合 TokenWindowMemory policy（超预算裁剪）+ 自实现 LlmCompactor（LLM 生成滚动摘要）。不引入 tokenizer（原则 2）——HeuristicTokenCounter::openai() = chars/4，与原手写 estimate_tokens 同语义。

模型上下文窗口动态获取：context_window.rs 四层 fallback（用户配置 > /v1/models 探测 > Ollama /api/show > 默认 100K），1h 缓存，配置变更 invalidate_cache() 清空。真实 usage 落库（rig 流式上报 CompletionCall 含 Usage，过滤全 0 哨兵后落库到 assistant 消息）。

2.4本体建模核心链路：从数据源到知识图谱

三期夯实本体建模的全链路闭环——用户注册异构数据源 → DataFusion 单进程联邦查询 → 本体层定义 ObjectType / LinkType / ActionType → Agent 通过 TextQL 自主跨源查询验证模型。SQLite 单库统一存储，零 JVM 零独立进程。

联邦查询的安全护栏

crates/federation/src/query.rs 实现只读查询执行：sqlparser 解析，仅 Query/Explain(Query) 放行（拒绝 DDL/DML），自动 LIMIT 注入（默认 200，max 1000），30s 超时。schema 浏览走三段式 {catalog}.information_schema.tables WHERE table_schema='public' 避开系统表，table_provider 回退。

DataFusion 54 已知限制
deregister_catalog 不存在，catalog 随进程留存（重启不恢复，启动时 restore_data_sources 重新注册）；CSV 无法直接注册为带 schema provider 的 catalog，改走 temp table 模式。

TextQL 与本体：LLM 生成意图，sqlparser 生成 SQL

决策 11 用 sqlparser 0.62（ANSI SQL:2011）替代 Python sqlglot——原方案需 Python 运行时违反原则 1。TextQL 的自然语言→逻辑计划部分走 LLM（复用 agent-core 的 Rig），非硬编码规则。LLM 产出结构化意图，sqlparser-rs 负责语法正确的 SQL 生成，TextQL→逻辑计划→各源方言 SQL 三段式编译，逻辑层与 DataFusion 的逻辑计划自然衔接。

本体元数据（ObjectType/LinkType/ActionType/数据源注册/凭证）全部存入 memory crate 的同一 SQLite .db，新增 ontology 表族（决策 10）——否决 PostgreSQL（独立进程违反原则 1）、嵌入式 PostgreSQL（体积过大）。单文件 ~/.onto-studio/onto-studio.db 便携备份。

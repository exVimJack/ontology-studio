# AI 建模与双模型协同校验工作流

> 本文档定义从「29 句话」到「可验证 Turtle 本体」的闭环工作流——大模型 A 生成、大模型 B 审计、逻辑博弈、专家仲裁、可视化校验、测试用例验证。对齐《本体驱动的AI数据管理》第 6.2 节。

## 一、大模型 A 生成（本体转化生成者）

### 输入要素
1. 审核通过的 29 句话业务描述
2. 《业务术语词典》
3. 系统指令（Prompt）——激发 AI 本体建模思维

### Prompt 示例

```
你是一个本体建模专家，任务是将自然语言业务描述转化为符合W3C规范的OWL本体。
请严格遵循以下要求：

【角色与任务】基于提供的业务术语词典和29条业务描述，构建一个结构化的本体模型。
核心任务包括：识别并定义类与属性、构建继承层级、形式化业务规则、统一术语体系。

【输入】你将收到以7类语义规范分类的标准化描述语句（29句话）。

【输出格式】以Turtle语法输出完整本体。必须明确包含：
1) 使用owl:Class定义的核心类及其rdfs:subClassOf层级；
2) 使用owl:ObjectProperty和owl:DatatypeProperty定义的关系与属性；
3) 使用skos:ConceptScheme/skos:prefLabel/skos:altLabel统一的业务术语；
4) 使用swrl:Imp形式化的SWRL业务规则（含swrlb:内置谓词）；
5) 使用owl:Restriction表达的值域合规规则（第2.5类）。

【质量规范】所有术语必须与《业务术语词典》一致，严格遵循W3C本体语义规范映射，
确保语义精准无歧义。每个实体的rdfs:comment末尾标注置信度[confirmed/high/tentative]。
业务操作（创建/审批/取消等）不入本体层，记入附属open_questions的business_operations。
```

### 优势（书中所述）
- **精准适配与自动转化**：大模型充当"语义编译官"，把 29 句话映射为 RDF/OWL/SKOS/SWRL 结构。识别语境差异（如区分组合/聚合关系），选择精准本体语义谓词。
- **智能构建与语义校验**：生成时主动检查本体语义自洽性，识别潜在漏洞（规则冲突、对象关系矛盾）并提示修正。"建模即校验"。
- **效率与质量双提升**：将数周工作缩短至分钟级，内置 W3C 规范校验。

## 二、大模型 B 审计（逻辑审计者）

### 为什么需要双模型
- **克服单模型局限**：不同模型在逻辑推理、规范理解上各有侧重，协同互补盲点。
- **提升校验深度**：从语法合规性深入到逻辑合理性、业务贴合度、设计最优性。
- **模拟专家评审会**：通过模型"辩论"显性化潜在问题，提升专家复核效率。

### 角色分工（异构协同）
- **大模型 A**（生成者）：负责语义重构与编码。
- **大模型 B**（审计者）：以 W3C 规范为基准进行逻辑扫描，独立查找缺陷。

### 大模型 B Prompt 示例

```
【角色】你是本体质量审计专家。核心任务是严格审视给定的本体模型，找出潜在缺陷。

【输入】1) 大模型A生成的本体文件；2) 29句原始业务描述。

【审计维度】请从以下维度审计，生成结构化报告：
1) 语法与规范性：
   本体是否符合RDF/OWL/SKOS/SWRL标准语法？是否遵循命名规范（类PascalCase/属性camelCase）？
   前缀声明是否完整（rdf/rdfs/owl/xsd + skos/swrl/swrlb）？
2) 逻辑一致性：
   是否存在类循环继承、属性定义域/值域冲突或SWRL规则矛盾？
   例如：病害与虫害的防治属性是否混用？农药的使用对象定义是否清晰？
3) 业务贴合度：
   本体中的类、属性、规则是否完全覆盖且精准对应原始业务描述？
   是否存在语义丢失或偏差？29句话是否每条都有对应本体产出？
4) 7+1规范覆盖度：
   第1类(RDF)/第2类(OWL)/第3类(SKOS)/第4类(SWRL)/第7类(SPARQL)是否主产完整？
   第5类(OWL-S)/第6类(ODRL)进阶是否按需产出？
   +1类(目标评估)是否进open_questions？

【输出】按"严重级别[error/warning]–问题描述–本体位置–修改建议"格式列出所有发现。
```

## 三、三个关键步骤

### 第一步：交叉互审

- **大模型 A**：基于 29 句话生成初步本体文件。
- **大模型 B**：接收 A 生成的本体 + 原始 29 句话，独立查找逻辑断点、语法错误、规则冲突。

### 第二步：逻辑博弈

当大模型 B 发现问题，将反馈同步给 A。

**大模型 A 辩护与修订 Prompt 示例**：
```
你收到了审计报告。请逐一审查所有问题：
1) 对于确实存在的错误，直接修正本体；
2) 对于认为审计有误的质疑，提供基于业务描述和本体规范的逻辑辩护理由。
请输出修订后的本体V2.0，并附"辩护与修订说明"。
```

**示例**：大模型 B 指出"荔枝霜疫霉病"与"荔枝炭疽病"在叶片病斑症状描述上重叠易误判，大模型 A 重新细化两种病害的关键鉴别特征，并调整诊断规则。

### 第三步：专家共识与最终仲裁

- 双模型交叉验证，**结论一致则自动通过**。
- 若对核心规则产生争议，将分歧点提取推送**人工终审**环节，由业务专家和工程师完成最终裁决。

## 四、可视化工具语法校验与专家内容把关

### 三步深度把关

**第一步：全局拓扑审查**（重点：对象与关系）
- 操作：展开本体层级树，查看类父子继承关系。
- 核心点：检查是否存在"分类不当"。如虫害和病害为不相交类（`owl:disjointWith`）。

**第二步：局部语义穿透**（重点：属性与约束）
- 操作：单击核心节点，查看 DatatypeProperty 和 ObjectProperty。
- 核心点：除数值区间（Range）校验外，重点检查**属性逻辑特征**（Property Characteristic）：
  1. `owl:FunctionalProperty`（函数属性）：多对一唯一性。如"当前最优推荐农药"特定防治期每病害仅一种。
  2. `owl:InverseFunctionalProperty`（反函数）：值唯一标识主体。如"农药登记证号"唯一对应农药。
  3. `owl:TransitiveProperty`（传递属性）：层级链完整性。如"病害子类"传递，自动补全分类体系。
  4. `owl:inverseOf`（逆属性）：双向关系闭环。如"防治"与"被防治"互逆，支持双向推理。

**第三步：规则路径回溯**（重点：规则与行动）
- 操作：模拟推理路径，检验 SWRL 规则、OWL-S 操作、ODRL 权限的触发效果。
- 核心点：确认"如果...那么..."决策规则逻辑链是否漏掉关键前置条件；验证权限触发条件；验证 AI 能否根据推理出的业务状态自动匹配 IOPE（输入/输出/前提/效果）。

### 典型迭代示例

- **AI 生成描述**：传感器监测到虫害迹象，系统自动启动无人机喷洒农药。
- **可视化呈现**：[虫害监测节点] 通过"触发"关系直接连接 [无人机施药动作]。
- **专家把关**：植保专家指出"必须引入环境约束和害虫阈值判断。雨天不能喷药，且必须确认虫密度达到防治指标"。
- **迭代**：本体增加 [气象条件核验] 和 [防治阈值判定] 节点，设置逻辑属性"降雨量<0.5mm 且虫口密度>阈值"为触发喷洒必要前提。
- **结果**：模型从"感应即动作"线性逻辑，优化为具备多维约束的智能决策闭环。

## 五、测试用例验证

### 价值
- **验证 7+1 规范业务覆盖度**：确保模型能解析 29 句话每条陈述，回答跨多个语义维度的复合业务问题。
- **量化模型成熟度**：提供客观测试通过率，定位薄弱环节（某类规则频繁失效）。
- **构建可回归资产**：形成可复用场景化测试集，确保模型未来扩展时核心逻辑不受破坏。
- **暴露深层逻辑与性能隐患**：注入边缘/异常数据，主动发现规则冲突、推理死循环、性能瓶颈。

### 人机双驱验证过程

**第一步：专家定义"黄金测试用例"**
- 基于核心业务流程、关键决策点、典型异常场景，编写测试场景、核心问题、预期结果。
- 示例：核心问题"日均温 28℃、湿度 85% 以上时，如何防治荔枝蒂蛀虫？"，预期结果需明确药物名称、施用浓度、间隔时间。

**第二步：AI 自主构建测试矩阵**
- 基于已构建本体和专家种子用例，大模型自动生成：
  - **边缘用例**：气温 20℃、湿度 60%，但虫害密度异常高时，是否仍触发预警？
  - **异常用例**：同时检测到蒂蛀虫和卷叶蛾，防治建议是否存在冲突或优先级错误？
  - **压力测试**：千个果园并发查询防治建议，推理引擎响应时间是否达标？

**第三步：验证与结果回溯**
- 将问题转化为 SPARQL 查询，在本体上运行。
- 对比实际输出与预期结果，生成测试报告（通过/失败/错误）。
- 失败用例分析根源（模型缺陷/用例错误/规则冲突），修正本体的类关系或规则。

## 六、工作流总结

```
29句话 + 术语词典 + Prompt
    ↓
大模型A生成Turtle（V1）
    ↓
大模型B审计（语法/逻辑/业务贴合/7+1覆盖）→ 结构化报告
    ↓
大模型A辩护修订 → Turtle V2 + 辩护说明
    ↓
双模型一致？─否─→ 专家仲裁分歧点
    ↓是
可视化校验（拓扑/语义穿透/规则回溯）→ 专家迭代
    ↓
测试用例验证（黄金用例 + AI矩阵）→ 修正
    ↓
validate_ontology_ttl → import_ontology_ttl（落库）
```

## 七、宪章与变更日志（W3C 路线专用）

W3C 路线的 charter 和 changelog 用**双轨制**记录：

### 1. charter（本体设计宪章，不变点）——双轨并存

| 轨道 | 载体 | 工具 | 用途 |
|---|---|---|---|
| 结构化索引 | SQLite `ontology_ttl_charter` 表 | `set_ontology_ttl_charter` / `list_ontology_ttl` | 可查询、可 UI 展示 |
| W3C 原生词汇 | .ttl 文本内 | 手写（validate→import） | 产物中立、可被任何 RDF 工具消费 |

**结构化索引**（工具落库）——四字段语义：
- `business_scenario`：业务场景（服务于什么业务目标、谁用、解决什么问题）
- `business_essence`：业务本质（核心业务对象/状态/关系/动态行为的一句话本质概括）
- `design_intent`：设计意图（为什么这样建模、够用且可扩展的取舍、可扩展方向）
- `invariants`：补充说明（自由文本，记录不可违反的业务约束、边界条件等）

**W3C 原生词汇**（同步写进 .ttl，对应关系）：
```turtle
@prefix dcterms: <http://purl.org/dc/terms/> .
@prefix skos: <http://www.w3.org/2004/02/skos/core#> .

<https://example.org/ontology/procurement#ProcurementOntology>
    a owl:Ontology ;
    dcterms:title "采购本体"@zh ;              # ← business_scenario
    skos:definition "覆盖采购订单/供应商/对账"@zh ; # ← business_essence
    rdfs:comment "够用且可扩展，预留结算扩展点"@zh ;# ← design_intent
    skos:scopeNote "供应商编号全局唯一"@zh ;        # ← invariants
    owl:versionInfo "1.0.0" .
```

> **为什么双轨**：结构化索引支持 SPARQL/SQL 查询与前端面板展示；W3C 原生词汇保证 .ttl 产物自包含、可被任何 RDF 工具（Protege、Apache Jena、Oxigraph CLI 等）消费。两者字段一一对应，更新时同步。

### 2. changelog（变更日志，变化点）——SQLite 结构化索引

每次 `import_ontology_ttl` 或 `delete_ontology` 之后，调用 `commit_ontology_ttl_change` 提交一条 git commit message 式记录：

- `title`：一句话标题（如「给 18 个子类补 a owl:Class」）
- `body`：设计说明正文——为什么改、整体思路、影响范围
- `change_summary`：机器可读 JSON 摘要（如 `{"modified":["Anchor","StoreManager",...]}`）
- `revision`：本体内从 1 递增（由 store 自动分配）

**为什么 changelog 不写进 .ttl**：changelog 是「随历史增长」的变化点，写进 .ttl 会让本体定义与历史记录混杂，破坏本体的「定义层」纯净性。用 SQLite `ontology_ttl_changelog` 表存（git commit log 式），与本体定义物理分离、语义分离、写入路径分离——这跟 charter（不变点，可双轨）不同。

### 3. 闭环流程

```
冷启动：import_ontology_ttl → set_ontology_ttl_charter（写宪章）
                              → commit_ontology_ttl_change（记初始导入）

增量：export → 改 .ttl → validate → import(overwrite=true)
                              → commit_ontology_ttl_change（记本次变更）

查历史：list_ontology_ttl_changelog（回溯演进过程与设计决策）
```

## 二、推理层决策：暂不内置（留白）

### 决策

**当前不集成 OWL/SWRL 推理引擎**，复杂推理（第 2 类 OWL RL 物化、第 4 类 SWRL 规则执行）留白，未来真有需求再评估。

### 决策依据（oxigraph 官方设计哲学）

oxigraph 不内置推理是**深思熟虑的设计决策**，非技术缺陷：

1. **专注核心目标**：oxigraph 定位是高性能可嵌入 RDF 三元组存储 + SPARQL 引擎，首要目标是完全兼容 SPARQL 标准。性能优化（如并行执行）优先级高于推理。
2. **架构复杂度**：高性能增量推理机需深度访问 oxigraph 内部数据结构，会破坏模块化设计。
3. **集成难度**：曾考虑集成 Rust 推理库 `reasonable`，但会造成循环依赖（oxigraph → reasonable → oxigraph）。
4. **轻量化原则**：保持自身轻量高效可维护，将推理留给外部工具或 SPARQL 更新实现。这符合 AGENTS.md 原则 2「轻量化」。

### 推理缺口的应对路径

#### 路径 A：SPARQL「模拟」推理（短期，简单规则）

利用 oxigraph 支持的 SPARQL UPDATE（`INSERT`/`CONSTRUCT`）手动推导存储新事实：

```sparql
# 计算rdfs:subClassOf的传递闭包（第2.1类的传递属性）
INSERT { ?s rdfs:subClassOf ?o } WHERE { ?s rdfs:subClassOf+ ?o }
```

- **适用**：第 2 类的 `rdfs:subClassOf` 传递闭包、简单属性继承等。
- **局限**：需手动维护，复杂推理（OWL RL 全量）支持有限。

#### 路径 B：LLM 解读执行（对齐书 6.2 思路）

SWRL 规则（第 4 类）的"如果...那么..."业务逻辑，由 LLM 解读执行——书 6.2 本就规划"大模型充当语义编译官"，SWRL 是给人/LLM 读的业务规则表达，不强制推理机原生执行。

- **适用**：第 4 类 SWRL 业务触发规则、第 5 类 OWL-S 流程 IOPE 匹配。
- **优势**：对齐书的方法论，AI Agent 通过 SPARQL 取本体（第 7 类），LLM 推理执行规则。

#### 路径 C：未来集成 reasonable（如真有需求）

`reasonable` crate（BSD-3-Clause，13.9 万下载，2020 年至今维护，纯 Rust 库）支持 OWL 2 RL 推理。若未来需要确定性 OWL RL 物化，可评估集成（需解决循环依赖——通过独立推理服务或物化结果回写 oxigraph）。

- **当前不集成**：避免过早引入复杂度，遵循"先走通方法论再实现"。

## 三、工具链设计

### 三个 agent 工具（与 skill 方法论对齐）

| 工具 | 作用 | 实现 |
|------|------|------|
| `export_ontology_ttl(ontology_iri)` | 导出当前本体完整 Turtle | oxigraph 查询 + oxttl 序列化 |
| `validate_ontology_ttl(ttl_content)` | 校验 Turtle 语法 + 7+1 语义一致性 | oxttl 解析 + 规则检查 |
| `import_ontology_ttl(ttl_content, overwrite?)` | 解析 Turtle 落库 | oxttl 解析 + oxigraph 存储 |

> oxttl 是 oxigraph 的序列化子模块，无需单独引入。

### crate 扩展方案（onto-studio）

`crates/ontology-store` 扩展：
- 新增 `ttl.rs` 模块：oxttl 解析/序列化 + oxigraph 存储
- Cargo.toml 加 `oxigraph = "<version>"`
- 不新增独立 W3C 表族——直接用 oxigraph 的原生图存储（非 SQLite 关系表），支持 SPARQL 查询
- 这与 Gaia 表族（ObjectType/LinkType 等关系表）隔离，两套独立存储

## 四、落地工程五环（对齐书 6 章 ③④⑤）

本 skill 聚焦①②（预处理 + AI 建模），③④⑤ 是落地工程层：

### ③ 入库（书 6.3）

**本体资产存入语义数据库**（oxigraph）：
- **规范化注册与治理**：每个本体建立全局唯一资产标识、元数据档案、访问地址，纳入企业资产目录。
- **质量审查**：入库强制执行质量与合规性检查（表 6-4 入库质量审查标准）。
- **服务化发布**：自动配置可被上层应用调用的稳定服务端点（SPARQL 端点）。

**数据层+语义层双重运维**：
- 数据层：存储、性能、延迟、权限。
- 语义层：术语一致性、规则冲突、业务适配。
- 核心指标：问题发现及时性、优化有效性、资产稳定性、运维高效性。

**"建用优复"全生命周期**：
- 构建（建模）→ 使用（应用）→ 优化（迭代）→ 复用（共享）。
- 资产增删改查控：注册发布、发现复用、变更版本管理、权限安全。

### ④ 平台（书 6.4）

**三类核心角色协同**：
- **本体建模 Agent**：领域知识→语义规范本体，自动化建模+一致性校验。
- **业务专家**：业务语义与领域规则审阅，确保反映真实业务逻辑。
- **应用验证 Agent**：场景语义推理验证+应用测试，评估可用性有效性。

**平台核心能力**：
- 多模态输入（Talk 自然语言 / Code 程序资产 / Diagram 流程图 / Data 样本数据）→ 智能转化 → 实时自校验。
- 图形化可视化：映射 7+1 语义规范多维度透视，力导向图布局，逻辑路径回溯，一键跳转编辑。

### ⑤ 点线面实施（书 6.5）

**避免"大而全"顶层设计陷阱，渐进式构建**：

**点（小切口场景）**：
- 高价值、小切口、快见效的具体业务场景切入（如荔枝尺蠖防治）。
- 业务发起、IT赋能，最小数据集+量化规则，快速形成价值闭环。
- 四步法：定义场景 → 建模连接 → 开发MVP微应用 → 闭环验证迭代。

**线（纵轴整合）**：
- 纵向整合多个相关场景本体，沿"公共层→领域层→实例层→动作层"四层架构拉通。
- 消除领域内语义歧义与模型冗余，建立可复用核心概念与规则库。
- 四步法：实例层关联 → 领域层统一 → 公共层对齐 → 动作层标准化。

**面（横轴贯通）**：
- 跨领域横向语义贯通（如病虫害+种植管理+气象服务+市场销售）。
- 建立跨领域术语映射表、桥接本体、联邦查询机制。
- 三步法：识别跨域核心交互点 → 建立语义映射与对齐规则 → 构建桥接本体与联邦查询。

**存量数据连接**：
- 整合存量数据湖与知识图谱，渐进式演进：资产整合（1.0）→ 增量创新（2.0）→ 战略统一（3.0）。

## 五、与 Gaia 表族的关系

onto-studio 现有 Gaia 表族（ObjectType/LinkType/ActionType/Dataset，SQLite 关系表）与本 skill 的 W3C 语义存储（oxigraph 图存储）**隔离**：

| 维度 | Gaia 表族 | W3C 语义存储 |
|------|----------|-------------|
| 世界假设 | 封闭世界 | 开放世界 |
| 存储引擎 | SQLite 关系表 | oxigraph 图数据库 |
| 查询语言 | 自定义 | SPARQL 1.1 |
| 产物格式 | OntologyPayload JSON | Turtle (.ttl) |
| 方法论根源 | Palantir 风格 | 7+1 语义规范（《本体驱动的AI数据管理》） |

两套独立，当前不互通。未来可评估双向转换器（Gaia ObjectType ↔ owl:Class 等），但需先各自走通方法论再考虑合并。
